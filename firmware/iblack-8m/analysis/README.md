# iBlack / iermu ファームウェア静的解析・追加結果

## 対象と範囲

ユーザー提供の `iblack_1.bin` と展開ZIPを対象にした静的解析。カメラへコマンドを送らず、ファームウェアを実行せず、フラッシュ・DNS・Wi-Fi・配信サービスは変更していない。以下は**このダンプ内の実装**についての結果であり、稼働中の2台の状態を測定した結果ではない。

| --- | --- |
| `iblack_1.bin`（8 MiB） | `b3e0ff253ed30696af53ecadb4ccf4e4220c6d6c6e38ce6730f4fe86e4a80da0` |
| `cmsMain.out` | `4419e7f86607eb83337de021563db2bb7392040059b29b715090e2ba54572e56` |
| `SysUpdate` | `c76e218d9dffde035ca5ed28cae89fa2dd679c539f647f6329f8dcf083e0c6d9` |

Seafile版とCatbox版の中身3ファイルは一致。添付の元 `firmware_analysis.md` に書かれたダンプのハッシュは62桁で、実物の64桁ハッシュとは一致しない（元資料の記載誤り）。上表は実物の値。[^https://sea.salvare.me/seafdav/NotionAI/iermu-camera/iblack_1.bin]

## 1. DNS設定と実際のnameserver一覧は同じではない

`cmsMain.out:0x5b954` は `/app/etc/resolv.conf` を生成する。rootfsの `/etc/resolv.conf` はそこへのリンク。生成処理には、設定値・DHCP由来リストのほか、**114.114.114.114 と 8.8.8.8 を追加する実装**がある。[^https://sea.salvare.me/seafdav/NotionAI/iermu-camera/iblack_firmware_extracted.zip]

追跡した内部値は以下。

- `0x64b9c` が返す `context+0xdf2c` は、ログと経路設定への使用から **ゲートウェイ**。DNS1のgetterと混同しない。
- `0x64dc8` が返す `context+0xdf30` は、設定DNSとして生成処理に使用される。
- `0xb4204` は追加のDNS候補リストへのポインタを返す。DHCP処理側にも同じ領域への参照がある。
- Wi-Fi接続完了経路の `0x699f8` からも生成関数が呼ばれる。

生成順の概略（G=ゲートウェイ、D=設定DNS、H=追加候補）:

```text
D が 0 / G / 8.8.8.8 のいずれでもなければ D を追加
H から G・すでに追加したD・8.8.8.8・114.114.114.114 を除いて追加
D が114.114.114.114でなければ 114.114.114.114 を追加
8.8.8.8 を追加
G が0でなければ G を追加
```

通常の非ゼロのゲートウェイとLinuxのDNSアドレスを指定しても、Linuxだけの一覧にはならない。公開DNSの追加は、ここでは「Linuxへの問い合わせが失敗した後にだけ実行する処理」ではなく、**設定ファイル生成時の追加**である。実際にどのサーバーへ問い合わせるか・再試行するかは、resolver側の処理とネットワーク状態も別途確認が必要。

### 運用への意味

「設定値がLinuxになっている」「LinuxでDNS問い合わせを観測した」は、どちらも「他のDNSを一切使わない」の証明にはならない。専用化するには、経路上でカメラのTCP/UDP 53番をLinuxに制限・転送する方法、または本体の生成処理を変更する方法が候補。Linuxが通信経路上にいないなら、Linux自身のiptablesだけでは他宛て通信を捕捉できない。**今回はどちらも適用していない。**

従来ツールが扱う44-byte設定のDNS欄と、この内部処理で参照する値は区別する。特に第2DNS欄がこの生成関数でどう扱われるかは未確定で、DNS1/DNS2がそのまま2行になるという前提は置かない。

## 2. UARTは「完全無効」ではなく、起動時gettyの経路がある

起動スクリプト `cmssysrun.sh` に次の起動がある。[^https://sea.salvare.me/seafdav/NotionAI/iermu-camera/iblack_firmware_extracted.zip]

```sh
/sbin/getty -L ttyS000 115200 vt100 -t 5 &
```

- `inittab` の常時respawn行はコメントアウトされている。
- U-Bootの入出力はserial、速度は115200。
- rootのパスワード欄は空ではない。自動rootログインが成立するとはいえない。
- `-t 5` と常時respawnがない構成なので、恒久的なログイン待受ともいえない。

`cmsMain.out:0x81658` のPTZ初期化には、特定のハードウェア分岐で `/proc/<pid>/fd/0` のリンク先を読み、`ttyS000` 使用を検出するコードがある。検出時 `0x81ba4` はメモリを解放し、`noPTZdev` 相当のフラグを立てる。**この分岐はgettyをkillする処理ではなかった。** コンソールとPTZの競合回避を示す実装と解釈できるが、ピン配置・電圧・実機ログインは未検証。

通信からUARTコンソールを恒久的にONにするパラメータは、まだ特定していない。

## 3. 更新プログラムはTCP 3508の独立サービスを持つ

`SysUpdate` の `0xca50..0xcb1c` を追跡すると、TCPソケットを作り、`0.0.0.0:3508` にbindしてlistenする。ポートは文字列だけでなく、sockaddrへ書き込むバイト列から確認。先頭28-byteメッセージを読み、CRCを比較してからコマンド分岐へ進む。[^https://sea.salvare.me/seafdav/NotionAI/iermu-camera/iblack_firmware_extracted.zip]

一方、引数付き `SysUpdate 3508` は同じ待受をもう一つ起動するのではなく、`0xe954..0xea38` で **127.0.0.1:3508へ接続するローカル制御クライアント**になる。送る制御の最終的な効果は、この段階では確定していない。

MTDデバイスを開き、書込み処理へ進む分岐もある。これはCMSの3357番や、これまで調べた3566番と同一視できない別経路。稼働中カメラの3508番の待受確認や、更新・消去・再起動のパケット送信は行っていない。入口のCRC確認だけから、認証・署名が不要と断定もしない。

## 4. 更新ファイルの取得・検証を具体化できた

`cmsMain.out` の更新処理に、ホストとパスから次のコマンドを組み立てる経路がある。HTTPでカメラ自身がファイルを取得する処理であり、APKがファーム全体を直接送る処理とは別。[^https://sea.salvare.me/seafdav/NotionAI/iermu-camera/iblack_firmware_extracted.zip]

```text
wget -q -O /app/etc/a0b0.bin http://<host><path>
```

- 取得コマンド組立と実行: `0x89cd4..0x89d14`
- ファイル検査関数: `0x89404`
- **36-byte（0x24）ヘッダー**を読み、先頭8個のlittle-endian 32-bit値の加算値を末尾の32-bit値と比較。
- 型・互換性に関係する追加フィールドも比較している。各フィールドの正確な製品上の意味には未確定部分がある。
- 別の経路では、データ変換処理の後に32-bit加算チェックサムを比較する（`0x89e08..0x89f94`）。
- 変換初期化には固定キー由来の処理がある。キー値を本レポート本文へ転記していない。バイナリ原本は `../original/` と `../extracted/` に保持する。

ここで確認できた加算チェックサムは真正性を保証する電子署名と同じものではない。ただし、**更新全体で署名がないとは未確定**。実際のメーカー配布更新ファイルがないため、復号・受理・書込み成功は試していない。8 MiBのSPIフラッシュダンプと配布更新パッケージを同じ形式として扱ってはいけない。

## 5. カメラ自身が外へRTMP送信する実装もある

`0xbe388..0xbe3f8` で、サーバー候補とストリーム識別子から `rtmp://<server>/live/<stream>` を作って送信側の処理へ渡している。さらに `0xbe458..0xbe520` では `GUID` / `PUBLISHTOKEN` に関係する引数、コールバック、prepare処理を設定する。[^https://sea.salvare.me/seafdav/NotionAI/iermu-camera/iblack_firmware_extracted.zip]

これは、これまで作った「Linuxがカメラの映像を取得して中継する経路」とは別の、**カメラ発の送信経路がファーム内に存在する**証拠になる。

ただし、ホスト名のDNS置換だけでは、サーバー候補の用意・開始状態・認証関連情報・送信準備まで成立しない。まだローカルサーバーへの自動プッシュにはつながっていない。API応答のどの項目がどの内部状態を満たすのか、認証情報の生成や更新まで含めた対応付けが次の調査対象。

## 使った手法

1. ZIPの安全性、サイズ、ハッシュ、パーティションと既存展開結果を確認。
2. ARM32 little-endian ELFをpyelftoolsで読み、Capstoneで静的逆アセンブル。
3. PC相対リテラル参照、BLの呼出し先、PLTとインポート関数を対応付け。
4. 文字列の存在だけでは結論にせず、条件分岐・引数・実際の呼出し先を照合。
5. 共有文字列の途中を指すポインタを誤解しないよう、解析補助ツールを修正。
6. DNS生成モデルと更新ヘッダーのオフライン検査ツールを追加。解析ツールも含め**22テスト成功**。

### 添付ツール

`tools/offline_inspect.py` は標準Pythonのみで動き、ネットワーク通信・カメラ操作・書込み機能は持たない。

```sh
python3 tools/offline_inspect.py dns-order --gateway 192.0.2.1 --dns 192.0.2.22
python3 tools/offline_inspect.py update-header /path/to/update-package.bin
python3 -m unittest discover -s tools -p 'test_*.py'
```

`index_firmware.py` とそのテストには `capstone==5.0.3` と `pyelftools==0.32` が必要。更新ヘッダー検査は「観測した加算構造が合うか」を見るだけで、互換性・署名・安全な書込みの保証ではない。DNSモデルも実機の実測結果ではない。

## 次に詰める点

- 公開DNSへの迂回が実際に起きる条件と、resolver側の採用数・再試行順。
- 通信設定の第2DNS欄とOS生成ファイルの対応。
- RTMPサーバー候補・認証・開始指示のAPI応答と内部状態の対応。
- メーカー配布パッケージの実物を使った形式・変換・検証の照合。
- UARTの実機配線・起動ログ確認と、復旧経路の確認。

この静的解析では実機の変更・フラッシュ書込みは行っていない。Git収録版では、ユーザー指定によりダンプ原本・展開ZIP・全展開物を隣の `../original/` と `../extracted/` に保存する。APK由来ファイル・運用設定・通信ログは追加していない。
