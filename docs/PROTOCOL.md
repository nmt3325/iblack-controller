# 使用した制御通信

対象カメラとのセットアップ通信はTCP 3357番を使用します。ここでは、収録コードが実際に構成する要求メッセージと、今回の実行で確認した機体情報を記録します。

## 接続先

| 状態 | 接続先 |
| --- | --- |
| カメラのセットアップ用APへ接続中 | `192.168.58.1:3357` |
| 専用APへ参加後のカメラ | `192.168.10.34:3357` |

## 要求メッセージ

収録コードの `send_cmd` は、次の4バイトと本体を送ります。

```text
[main, sub, body_length & 0xff, (body_length >> 8) & 0xff] + body
```

これは要求側の形式です。応答側の通常長はビッグエンディアンです。後続の応答確認は末尾の節を参照してください。

| main/sub | 収録コードでの用途 |
| --- | --- |
| 5 / 17 | バージョン取得 |
| 69 / 6 | ログイン |
| 74 / 63 | MAC・iMacTypeを含む機体情報の取得 |
| 74 / 38 | Wi-Fi設定の読出し |
| 72 / 8 | Wi-Fi設定の送信 |
| 65 / 3 | 保存要求の送信 |

ログイン本体は40バイトで、ユーザー名を先頭、パスワードを20バイト目から格納します。実際の認証文字列はGit管理しません。

## 機体識別

取得したパラメータ本体の先頭6バイトをMACとして使用します。オフセット12の32bit値はコード内でビッグエンディアンとして読み、今回の対象機では `iMacType=0` を確認しました。この対象機の処理では追加の認証要求 `75/63` を送信しません。

セットアップ待受は、Wi-Fi設定の送信前に取得MACを期待MACと照合します。

## Wi-Fi設定本体

`72/8` の本体は97バイトです。

| オフセット | 長さ | 内容 |
| --- | --- | --- |
| 0 | 1 | `0` |
| 1 | 32 | SSID、残りはゼロ埋め |
| 33 | 32 | 先頭6バイトがASCII `******`、残りはゼロ |
| 65 | 32 | PSK、残りはゼロ埋め |

収録実装が格納するSSID/PSKの上限はそれぞれ32バイトです。今回設定したSSIDはASCIIの `iermu-cam` です。

## 設定保持の判定

今回の合格条件は、要求の送信だけでなく、カメラの電源を入れ直した後も追加の書き込みなしで同じAPへ戻ることです。2026-11-11 09:11:50の再接続とDHCP取得で、この条件を確認しました。


## 後続の応答確認と制御

`client/camctl.py` は応答main/subを照合し、通常の本体長をビッグエンディアンで読む。要求側の長さはリトルエンディアンのまま。

- `65/3` の `41 03 ff 00` は保存成功のステータス応答。65280バイトの本体長でも、保存拒否でもない。
- `72/8` の `48 08 ff 00` も成功。今回の専用SSID再設定では両方の応答後、実際のAP接続を確認した。
- GET/SETパラメータの `ff xx` は成功する長さとして扱わない。SET 75/41では通常長1・本体 `00` を確認した。
- `74/38` の2個のSSIDフィールドは確認したが、優先順位・フォールバックプロファイルという意味までは断定しない。`75/38` は本体 `01` を返し、実機設定は変化しなかった。Wi-Fi変更には `72/8` を使う。
- `74/41` のIR構造体は24バイト。先頭2個のBE16は今回25・15で、オフセット4のランタイム指定が0=自動、1=昼、2=夜。GETは現在モードを反映しないので、映像で切替・復帰を確認する。
- トークン構造体はアプリ上ではパラメータ39だが、この実機のGETは拒否された。アカウントやトークンの上書きは行っていない。
