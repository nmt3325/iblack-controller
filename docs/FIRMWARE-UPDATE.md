# iermu ファームウェア更新の調査

対象：Android `com.intl.iermu`、`1.8.0_1224`（577）。調査日：2026-11-12（日本時間）。

> **ダンプ入手後の追補：** [自作ファーム更新の実現性](FIRMWARE-SELF-UPDATE.md)で、`SysUpdate` のローカル更新経路を解析し、受信・復号・仮想MTD書込みまで19ケースを検証した。実機への書込み・自作ファームの起動は未確認。確認した命令はappfsとbakfsを同時に上書きする。**以下はAPK調査時点の記録であり、カメラ側を「未入手・未確認」とする箇所は追補の結果と区別する。**

## 結論

更新の入口は2系統ある。通常のカメラ更新はクラウドAPIへ開始を依頼する。別にNAS/SMB設定から呼ばれるCMSの `kernelUpgrade` がある。ただし後者も更新ファイルを転送する実装ではなく、5バイトの開始指示である。

**今回、クラウドの `upgrade`、CMS `75/42`、`75/47`、設定保存、再起動は実行していない。** 更新イメージの入手、実際の書換え、任意ファームの導入は未成立。稼働中の中継コード・設定・サービスは変更していない。

## 1. 通常更新：クラウド経路

```text
アプリのカメラ情報／一覧等
  → checkUpgradeVersion
  → POST https://api.iermu.com/v2/pcs/device : method=checkupgrade
  → バージョン・変更内容の確認画面
  → 利用者が更新を確定
  → checkCamFirmware / apiCamFirmware
  → 同じAPI : method=upgrade
  → 同じAPI : method=upgradestatus をポーリング
```

| 操作 | フォーム | アプリで読む応答 |
| --- | --- | --- |
| バージョン照会 | `method=checkupgrade`, `deviceid`, `access_token`, `lang` | `need_upgrade`, `version`, `desc` |
| 更新開始 | `method=upgrade`, `deviceid`, `access_token` | 共通の成功／失敗応答 |
| 状態照会 | `method=upgradestatus`, `deviceid`, `access_token` | `status`, `deviceid` |

**`checkCamFirmware()` は照会専用ではない。実際に `method=upgrade` を送る。** バージョン照会は別の `checkUpgradeVersion()` である。コード例を名前だけで判断して実機に呼び出さない。

この要求には更新ファイル、ファイルURL、ハッシュ、ハードウェア型番をアプリが追加する処理はない。機種選択がサーバ側で行われる可能性はあるが、その実装は未入手である。確認したアプリ側の経路は開始・表示・状態監視であり、カメラへのファーム本体転送やフラッシュ書換えコードではない。

### 画面の条件

- カメラ情報のバージョン欄：`needupdate == 1`、アプリ内進捗が初期値 `-1000`、電源OFFでもオフラインでもない場合に照会する。確認画面の確定後は `dataType == 0` の場合に更新開始へ進む。
- カメラ一覧：更新必要フラグに加えて `forceUpgrade`、オンライン・電源状態、`dataType`、既表示フラグで案内を分岐する。強制更新フラグがあるだけで、今回確認した確定ダイアログを経ずに自動更新するとまでは言えない。
- 設定画面の `upgrade_setting` クリック分岐は直接 `checkCamFirmware()` を呼ぶ。この分岐自体には追加の確認ダイアログがない。実際に常時表示されるかは別途の画面条件・機種状態に依存する。

### 状態と進捗表示

| status | 画面での扱い |
| --- | --- |
| `1` | 更新中／開始待ちの表示 |
| `2` | ダウンロード開始 |
| `3` | ダウンロード成功 |
| `4` | 更新適用中 |
| `5` | 更新成功、一覧を再取得 |
| `-1` | ダウンロード失敗 |
| `-2` | 更新失敗 |
| `0`、その他 | アプリ内進捗状態を初期化する分岐 |

更新開始成功後の監視は通常3秒間隔で、`5/-1/-2` が終了条件。5分経過を判定するコードもあるが、前のstatusオブジェクトを `-2` に変更した後、次のサーバ応答でstatusを置き換えるため、厳密な5分打切りとは断定できない。

一覧の進捗％はコールバックごとに1ずつ増加し、最大99で待つ表示である。ファイルの受信バイト数から計算した進捗ではない。

## 2. NAS/SMB設定からの更新：CMS経路

NAS設定の `isKerne && isSmb` を満たすと確認ダイアログを表示する。利用者が確定すると次の呼出しを行う。

```text
LocalRecordSetting / NasDataFragment / NasSettingFragment
  → MineRecordBusiness.kernelUpgrade
  → NasDevImpl.kernelUpgrade
  → カメラの接続先解決、CMS接続・ログイン
  → main=75, sub=42 (PARA3_HTTPUPDATE)
```

アプリが組み立てる本体は次の5バイト。

```text
00 50 02 00 00
```

- 先頭2バイトは `LanUtil.htons((short)80)`、すなわちネットワーク順のポート番号80。
- 続く値は固定の `2, 0, 0`。`2` の機器内部での厳密な意味は未確認。
- **この5バイト内には、更新URL、LinuxのIPアドレス、ファイル名、ファーム本体はない。**
- `CmsNetUtil.setDevParam` の自動 `65/3` 保存はsub42では行われない。ただし、保存コマンドを送らないことは、更新命令がフラッシュを書き換えないという意味ではない。

名称は `kernelUpgrade` だが、本当にLinuxカーネルだけを書き換えるのか、追加モジュール等も対象なのかはカメラ側の解析が必要。**LANから指示できることと、インターネット不要・任意イメージ送信可能であることは別である。** ポート80が入っているだけで、HTTPアップロード用のWeb画面があるとも断定できない。

### 更新必要フラグと完了判定

`getNasParam` は `74/62`（PARA3_NASCONF）を読み、応答の先頭バイトから次を取り出す。

```text
isKerne = (b[0] & 0x04) != 0
isSmb   = (b[0] & 0x80) != 0
```

ただしNAS設定画面ではSMB共有の選択結果も `isSmb` に反映するため、送信直前の条件は画面側の状態にも依存する。

更新開始の成功応答後は、最大120秒、1秒間隔でNAS設定を読み直す。読み取りが成功し `isKerne == false` になったことを、アプリは更新成功とみなす。新しいファームのハッシュや全フラッシュ領域を照合しているわけではない。今回この機体の現時点のフラグを新たに読んだり、更新完了を実機試験したりはしていない。

### 別の更新らしい定数

`PARA3_ENSUREUPDATE = 47` という宣言もあるが、アプリの更新経路での呼出しは特定できなかった。JADXが数値を定数名へ置き換えた結果、無関係なBase64/DES/SMB実装にも名前が現れる。文字列検索のヒットだけで別の更新機能や利用条件を認定しない。

## 3. 更新ファイルと検証方式の調査結果

| 調査項目 | 到達点 |
| --- | --- |
| APKに同梱されたファーム | `.bin/.img/.fw/.upg` 等、更新らしいファイル名、assets/rawを確認した範囲では見つからない。全ファイルの任意符号化を否定したものではない |
| 更新ファイルのURL | 確定できていない。バージョン応答のアプリ側モデルにもURLのパースはない |
| ネイティブライブラリ | `libcmsplayer.so`、`libcmsffmpeg.so`、`libSDK_topvdn.so` の更新関連文字列では、カメラ用更新ファイル転送処理を特定できなかった。シンボル／文字列の調査であり、全逆アセンブルの証明ではない |
| 実機のバージョン文字列 | 過去の `74/3` 応答に `A0C0V261`。型番・SoC・基板互換性まで判定できるものではない |
| 電子署名・ハッシュ検証 | 確認したアプリ経路ではファーム本体を検証していない。カメラ側の検証有無・方式は不明 |
| ハードウェア適合・ロールバック防止 | カメラ／サーバ側の実装未入手のため不明 |
| 書換え先・復旧手段 | MTD配置、ブートローダ、リカバリ、A/B構成等は未確認 |

公開検索では、この機体に適合すると検証できるファームを取得できなかった。APK内の公式FAQ URLはこの調査環境ではHTTP451で取得できず、`api.iermu.com` は調査ホストの名前解決に失敗した。環境・時点に依存する観測であり、メーカーサービス全体の終了を証明するものではない。アカウントトークンを使ったAPI照会・更新開始は行っていない。

## 4. 現在のDNS・ローカル中継との関係

DNSでメーカーのホスト名をLinuxへ向けても、更新のメタデータやファーム本体、機器の検証条件が自動的に揃うわけではない。現在のローカルクラウド受信は、これら更新APIを再実装したものではない。

`75/42` の存在は「クラウドAPI以外にも、カメラに更新を指示する入口がある」という収穫。ただし、これだけでLinuxから任意ファームを流し込める、署名を回避できる、UARTを有効化できるとは言えない。

次に必要なのは、**適合する正規更新イメージ、元ファームのダンプ、または更新時の実通信／シリアルログ**のいずれか。入手後、ヘッダ・機種識別・パーティション配置・整合性／署名検証・更新プログラム・UART設定をオフラインで確認する。実機の更新開始やフラッシュ書込みはその後の別作業である。
