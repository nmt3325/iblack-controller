# ネットワーク経由のtelnet起動・停止

## 到達点

TCP 3508 の `SysUpdate` に、ファームウェア更新とは別の **telnet起動・停止コマンド** がある。
対象の2台目 `192.168.10.29` で、以下を実機確認した。

1. 起動前はTCP 23が `Connection refused`。
2. 起動要求が `FE 00` を返し、TCP 23で `login:` プロンプトを確認。
3. 停止要求が `FE 00` を返し、TCP 23が再び閉じることを確認。
4. 再有効化が `FE 00` を返し、ログインプロンプトが再び現れることを確認。

**確認したのはtelnetデーモンの起動とログイン画面まで。OSへの認証成功やrootシェル取得とは別。**
ユーザー名・パスワードの試行はしていない。
1台目 `192.168.10.35` は状態確認だけで、起動コマンドは送っていない。

カメラの再起動、ファームウェア更新、設定の永続化、Wi-Fi/DNS変更は行っていない。
今回の起動は一時的なものとして扱い、再起動後の保持は未検証。
外部向けの23番ポート転送も追加していない。

有効化・停止・再有効化の後、TailscaleのRTMP受信先から両カメラ各3フレームの復号に成功した。
確認中に2台目の中継プロセスのPID変更も観測しており、連続無停止までは主張しない。
中継サービスを手動で再起動する操作は行っていない。

実機結果は [サニタイズ済み検証記録](../evidence/telnet-control-20261113.json) を参照。

## 使い方

リポジトリのルートで実行する。追加依存は `unicorn==2.1.4` のみ。
ファームウェア本体は既にこのリポジトリに含まれ、別のAPKアーカイブは不要。

```sh
python3 -m pip install -r requirements-telnet.txt

# 実機に一切接続せず、暗号処理と対象ハンドラーを隔離メモリ上で検証
python3 tools/iermu_telnet.py selftest

# 状態確認（23番ポートとログインプロンプトのみ。認証は行わない）
python3 tools/iermu_telnet.py status --host 192.168.10.29

# 有効化。--applyがないと制御要求を送信しない
python3 tools/iermu_telnet.py enable --host 192.168.10.29 --maintenance-time --apply

# Debian02等、カメラのLANへ届く端末から接続
# ここから先のOSログイン認証は別途必要
telnet 192.168.10.29 23

# 停止
python3 tools/iermu_telnet.py disable --host 192.168.10.29 --maintenance-time --apply
```

Debian02には既存の解析用Python依存先を使うラッパー `~/.local/bin/iermu-telnet` も配置した。
同ホストでは `python3 tools/iermu_telnet.py` をこのラッパーに置き換えれば、pip導入やPYTHONPATH指定は不要。

### 時刻チェック

通常の要求では、nonceに埋め込まれた時刻とカメラ内部時刻の範囲チェックがある。
今回、ホストの現在時刻で作った要求は `FF 49` を返した。
カメラの正確な内部時刻は未取得のため、時刻差の具体的な値は確定していない。

`--maintenance-time` は、ファームウェア自身が実装する `0xFEAD` 分岐を使い、
**その要求の時刻チェックだけを省略する**。カメラの時計や設定を書き換えるものではない。
このフラグを明示した要求で起動・停止・再有効化に成功した。
通常の時刻チェックを使う場合はこのフラグを省き、必要に応じ `--timestamp UNIX秒` を指定する。
エラー後の自動的なフラグ切替や別コマンドの総当たりは実装していない。

## 解析の根拠

一次資料は [抽出済みSysUpdate](../firmware/iblack-8m/extracted/base_rootfs/usr/bin/SysUpdate)。
このビルドの SHA-256 は以下。

```text
c76e218d9dffde035ca5ed28cae89fa2dd679c539f647f6329f8dcf083e0c6d9
```

ツールはこのハッシュとARM ELF32 little-endian形式を検証する。
異なるバイナリに同じアドレスを適用することは拒否する。
これだけで別の実機のファームウェアバージョンまで自動判定できるわけではない。

| 箇所（ELF仮想アドレス） | 意味 |
| --- | --- |
| `0xD768` | opcode `0x92`。telnet状態が0のとき、mode=0でハンドラーへ |
| `0xD878` | opcode `0x93`。telnet状態が1のとき、mode=1でハンドラーへ |
| `0x9EC4` | 要求ボディの検証・復号・telnet制御ハンドラー |
| `0xA0BC`〜`0xA110` | 日数フィールドが `0xFEAD` なら時刻範囲チェックを省略 |
| `0xA320` | `system()` 呼び出し。mode=0は `telnetd`、mode=1は `killall -9 telnetd` |
| `0xA324`〜`0xA344` | `FE 00` 応答後、28バイトのクライアントACKを受信 |
| `0x16CA4` | 暗号コンテキスト生成 |
| `0x16B00` | nonceからIVを設定。NULを含む入力の扱いにも注意 |
| `0x15C54` / `0x163A8` | 16バイトの暗号化 / 復号 |
| `0x8D34` | 応答ヘッダーを生成しCRCを付加 |

暗号はRC6型の演算構造を持つが、標準RC6の鍵スケジュールと同一とは仮定していない。
正確な既存バイナリ内の算術処理だけをUnicornで実行し、要求を生成する。
固定シードや派生鍵をソースコードへ転記したり、ログへ出力したりはしない。

### 送信する最小要求

送信内容は **ヘッダー28バイト＋ボディ48バイト**、成功応答後にACK28バイト。
ファームウェアのイメージデータやフラッシュ更新命令は含めない。

ヘッダー:

| offset | 長さ | 内容 |
| --- | --- | --- |
| 0 | 1 | `0x92` 有効化、または `0x93` 停止 |
| 1 | 1 | 0 |
| 2 | 2 | 日数、little-endian。保守用時刻フラグは `0xFEAD` |
| 4 | 4 | ボディ長48、big-endian |
| 8 | 16 | nonce / 時刻情報 |
| 24 | 4 | 先頭24バイトのCRC、big-endian |

ボディ:

| offset | 長さ | 内容 |
| --- | --- | --- |
| 0 | 4 | `0x01000001`、big-endian |
| 4 | 4 | 平文データ長12、big-endian |
| 8 | 20 | 0 |
| 28 | 4 | 後続の暗号文16バイトのCRC、big-endian |
| 32 | 16 | 平文12バイトの0＋平文CRC4バイトを暗号化したもの |

CRCは反転IEEE多項式 `0xEDB88320`、初期値・最終XORとも `0xFFFFFFEF`。
Pythonのzlibでは `(zlib.crc32(data, 0x10) ^ 0x10) & 0xffffffff` と一致する。

このハンドラーにはMTD書き込みや再起動の分岐は見つからない。
ただし **同じTCP 3508の他opcodeにはフラッシュ更新処理が存在する**。
ツールは `0x92`・`0x93` と成功ACK以外を生成できないよう限定している。

## 安全側の制約と検証

- 制御先は明示的なRFC1918のIPv4アドレスのみ。LANスキャンやホスト名解決はしない。
- `status` はTCP 23のみ。パスワードやアプリの認証情報を送らない。
- 制御要求には `--apply` が必須。
- 送信する要求は、まずメモリ上の同一ハンドラーで成功することを確認する。
- エミュレーターの `system()` は文字列を記録するだけで、ホストのコマンドは実行しない。
- ソケット・ファイル・syscall・不明な外部関数呼び出しは遮断。受信・送信はメモリのスタブ。
- MMIOとして参照される領域もホスト上の私有メモリであり、実機レジスタには触らない。
- 暗号往復、起動、停止、暗号文CRC不正、平文CRC不正、期限切れ、保守用時刻フラグをオフライン検証。
- 暗号文や鍵、未加工の通信キャプチャ、ログイン情報、部屋の映像・音声は検証記録へ収録しない。

`tests/test_iermu_telnet.py` は14件のオフラインテスト。
Unicornがない環境では、エミュレーションを使う4件だけを明示的にskipする。
既存の通常コントローラーはUnicornなしで動作する。

## 未確認・制限

- 再起動後のtelnet維持、永続起動、OSへのログイン、root権限取得は未実施。
- 1台目への起動・停止要求は未実施。
- メーカーの別ファームウェアや別機種への互換性は未確認。
- `SysUpdate` はtelnetの状態をプロセス内に保持する。別経路でtelnetを起動・停止した場合に、実際のポート状態と食い違う可能性がある。ツールは別opcodeや強制再起動で補正しない。
- 映像の連続無停止はこのtelnet確認だけでは証明できない。映像チェックとサービス状態の観測は検証記録に分けて保存する。
