# TCP 3356 の映像・マイク音声調査

## 結論

添付コードの対象は TCP **3356**。実機では3356が開いており、3566は接続拒否だった。
設定を書き換えず、3357で得た1個のログインセッションから3356を2接続し、映像とマイク音声の同時取得・個別復号に成功した。
製品運用中のTailscale中継はRTMPのままで、3356へ切り替えていない。

## 成功した通信手順

1. カメラのTCP3357でバージョン照会 `5/17`、ログイン `69/6`。
2. ログイン応答の4バイトをbig-endianのセッションIDとして解釈し、制御接続を保持。
3. TCP3356へ64バイトの要求を送る。
4. 映像用と音声用では、同じセッションで別々の3356接続を使用。

以下は**受信に成功した要求形式**。未調査の固定値の意味や、誤ったCRCを拒否するかは断定しない。

| オフセット | 長さ | 使用した値・形式 |
| --- | --- | --- |
| 0 | 4 | `0xDBFACF03` little-endian。送信バイトは `03 CF FA DB` |
| 4 | 4 | セッションID big-endian |
| 8 | 4 | `1` big-endian。詳細な意味は未確定 |
| 12 | 4 | `1`: 音声、`2`: 連続映像。big-endian |
| 16 | 4 | 添付コードでは `2`。`0/1/2`を試した範囲では映像は同じ画素数 |
| 20 | 8 | 0 |
| 28 | 32 | 0 |
| 60 | 4 | 先頭60バイトのCRC32、little-endian |

```python
import struct
import zlib

def request3356(session_id, media, selector16=2):
    # session_id is private runtime state: do not print or save it.
    head = struct.pack("<I", 0xDBFACF03)
    head += struct.pack(">6I", session_id, 1, media, selector16, 0, 0)
    head += bytes(32)
    return head + struct.pack("<I", zlib.crc32(head) & 0xffffffff)
```

オフセット12の `3` は、単独試験でH.264のIDRを1フレームだけ返した。静止画要求に似た挙動だが意味は未確定。**映像＋音声指定とは確認できていない**。

## 形式と復号結果

| 対象 | 実機で確認した内容 |
| --- | --- |
| 映像 `media=2` | MPEG-PS、PES E0、Annex-B H.264 Baseline、1024×288 |
| 映像のfps | H.264 VUIは25fps。長時間の実測fpsの保証ではない |
| 音声 `media=1` | PES C0の中にADTSヘッダー付きAAC-LC、11025Hz、mono |
| 同時受信 | 制御1接続＋3356の2接続で、映像256フレーム／音声109568サンプルを個別復号。両方終了コード0・デコードエラー0 |
| RTMPとの比較 | 同じ調査中にカメラの既存RTMPから1280×720とAAC音声を復号。3356側で720pを取得する要求は未発見 |

音声接続ではProgram Stream Mapがなく、汎用MPEG-PS自動判定はMP2と誤認した。PESヘッダーを除去し、既存のADTS付きデータを `-f aac` として渡すと復号できた。**新しいADTSヘッダーの付加やRTMP用の末尾補正は不要だった**。
映像もFLV補正を通さず復号できた。1024×288はデコード上の画素数で、表示アスペクト比の目視判定はしていない。

## 現行RTMPとの違い

- 両方ともLinuxがカメラへ接続して取得するLANのpull方式。カメラからLinuxへのクラウドpushではない。
- 現行はカメラRTMP→FLV補正→FFmpeg→MediaMTX。3356は3357ログイン→PS/PES取得で、形式と要求が異なる。
- 3356の映像には今回のRTMP用FLV末尾補正が不要だった一方、音声の別接続・PES取り出しが必要。
- カメラIPへ直接接続したので、映像取得そのものにDNS誘導は不要。DNSによるクラウド代替や再起動抑止の成否とは別の確認。

## 安全性・未確認範囲

- この調査で送信した3357制御はバージョン照会とログインのみ。Wi-Fi・DNS・IR・保存コマンドは送信していない。
- 室内映像・音声・生パケット・セッションID・認証情報はリポジトリへ保存していない。メディアはRAMだけで扱いnull出力へ復号。
- 単独試験のため既存publisherを一時停止し、finallyで復帰。後段の実再生確認で中継の不調を検出したため、設定を変えずMediaMTXとpublisherを再起動した。
- 復帰後、同ホストのTailscale IP上の既存URLから720p映像38フレームとAAC音声を復号し、終了コード0・エラー0。単にserviceがactiveという判定だけではない。
- 別Tailscaleノードのoracle-ubuntu-03からも同じ既存URLを再生し、720p映像44フレームとAAC音声を復号。終了コード0・エラー0だった。
- 本日の調査開始前に同じ実再生の基準測定をしておらず、中継不調を3356によるものとは断定できない。
- 高解像度指定、音声と映像のタイムスタンプ同期・多重化、長期安定性、カメラ再起動後の復帰、3356経由のスピーカー送信は未確認。

## 追加：PTS/DTSと接続別の分離

後続調査で、映像E0のPTS/DTS、音声C0のPTS（90kHz基準）を読み取った。音声要求の接続に映像E0が少量混入するため、接続種別だけでなくPES stream IDで分離する。約12秒で317映像フレーム・131072音声サンプルをエラー0で個別復号したが、同期多重化と長時間の同期は未検証。

同時期に既存RTMP中継の実再生が停止し、中継2サービスの再起動が必要だった。3356の調査との因果関係は未確定で、並行運用の安全性が確認済みとは扱わない。詳細は[本体追加調査](CAMERA-DEEPER.md)、根拠は[後続調査JSON](../evidence/camera-deeper-20261112.json)。
