# 本体追加調査：時刻情報・画質設定・音声送信・デバッグ候補

## 結論と実施範囲

3356のPES時刻情報、アプリの画質変更手順、スピーカー入力形式を追加で特定した。UART有効化、高解像度3356、スピーカー実音は未達成。通常配信を3356へ切り替えてはいない。

カメラ設定への書込み、保存、Wi-Fi・DNS・経路変更、カメラ再起動、音声送信は行っていない。映像・音声はRAMからFFmpegのnull出力へ流し、生メディアとパラメータ本体を保存していない。ただし、終了時の再生確認で既存中継の停止を検出したため、復旧としてLinux側の中継2サービスを再起動した。設定変更なし・サービス再起動なしを混同しない。

根拠：[識別子を除いた調査記録](../evidence/camera-deeper-20261112.json)。

## 1. 3356：映像と音声を同期させるための情報

3357ログイン後、同一セッションの3356を音声要求1・映像要求2の2接続に分け、約12秒受信した。

| 対象 | PES | 時刻情報 | 復号結果 |
| --- | --- | --- | --- |
| マイク音声 | C0 128個 | PTS、90kHz基準 | AAC-LC 11025Hz mono、131072サンプル、エラー0 |
| 映像 | E0 317個 | PTSとDTS、90kHz基準 | H.264 Baseline 1024×288、317フレーム、エラー0 |

- 音声用接続にもE0が2個混入した。接続先だけで音声と決めず、PESのstream IDで分離する必要がある。AAC復号にはC0だけを渡した。
- C0はPESヘッダー `80/80/5`、E0は `80/c0/10`。5バイトのPTS、10バイトのPTS+DTSを区別して読む。
- 音声PTSの経過は約11.806秒、映像は約11.889秒。先頭の映像PTSは音声より約22.1ms前だった。
- H.264情報上の25fpsに対し、この短い区間のPTS間隔は平均約26.6フレーム/秒相当だった。単純にH.264を25fps固定で並べ直すと元の時間軸を変えるおそれがある。
- 今後の同時再生は、元のPTS/DTSを保持した多重化を優先する。先頭時刻が近いことだけでは、口の動きとの同期・長時間のずれ・安定運転を合格とはしない。

要求のオフセット8の32bit値については、1で受信できた一方、0・2の短い試行ではデータ0バイトだった。この値を高画質スイッチとする根拠は得られていない。既知の要求形式は[3356調査](VIDEO3356.md)を参照。

## 2. アプリの「画質変更」が変更するもの

`NasDevImpl.getCodeGrade / setCodeGrade` を追跡した。

1. GET 74/76のオフセット34・35から機種系統を判定する。本機の読取りは `camType=1, type=1`。
2. GET 74/5で82バイトのCODESETを取得する。オフセット10..11を16bit big-endianとして読むと、本機は400だった。
3. アプリのこの機種系統の3段階は200・500・1000。変更時は元の設定を読み、オフセット8・9を0、10..11を選択値へ変更する。
4. 75/5で設定を送信し、65/3で保存する実装だった。

この値の単位は未確定で、明示的な解像度指定も見つかっていない。**画質段階の変更手順が分かったことと、3356を720pにできたことは別**。今回は設定も保存も実行していない。

## 3. スピーカー：形式と開始条件の絞り込み

- `AudioRecorder.java` は11025Hz、mono、PCM16bit。Android定数はchannelConfig=16、audioFormat=2。
- `libcmsplayer.so` の `audio_start` 内で `15 08` を設定する箇所を確認した。AAC AudioSpecificConfigとしてAAC-LC・11025Hz・monoに対応し、Java側の入力形式と整合する。
- `MineLiveFragment` は接続種別2なら `startLyyAudio()`、それ以外ならアカウントのBaiduAccessTokenを取得して `startBaiduAudio(token)` を呼ぶ。
- `VideoView` のBaidu側は非空トークンを要求する。Linyang側は空文字で `startAudio()` へ進む。いずれもプレイヤーが存在することが条件。

接続種別の定数はBAIDU=1、LINYANG=2で、**LAN/WANの区別ではない**。本機がどのバックエンドのどの認証を必要とするかを、この分岐だけでは決められない。形式を合わせた送信だけでスピーカーが鳴るともいえない。今回、音声は送っておらず、publish受理と実音は未確認。

静的解析元は既存の `com.intl.iermu 1.8.0_1224 (577)`。Javaの位置、ネイティブ関数アドレス、元資料のハッシュは調査JSONに記録した。

## 4. UART・デバッグ候補とバージョン候補

| パラメータ | 読取り結果 | 解釈の限界 |
| --- | --- | --- |
| 7：SERISET | 28バイト。オフセット8・20に32bit big-endianの9600 | シリアル設定らしいが、PTZ/RS485等の可能性が残り、Linuxコンソールとは未確認 |
| 48：GETDEBUG | 96バイト | バイナリ構造と用途は未解明。有効化成功を意味しない |
| 3：VERINFO | 122バイト。オフセット16に `A0C0V261` | バージョン文字列の候補。型番、SoC、代替ファーム対応の証拠ではない |

7・48にはASCIIのUART/tty/debug/telnet/boot/consoleは見つからなかったが、バイナリのため「機能が存在しない」とは判断しない。以前の静的解析でも、SERISETを送信するアプリ経路は確認できず、定数48の多数の出現は無関係な数値の誤帰属だった。UARTを通信だけで有効化できるコマンドは、依然として特定できていない。

その他に1・4・5・49・54・62・76のGET応答長を採取した。名前の定数があることや応答が返ることだけで、各機能が動作すると判定しない。

## 5. ポートと80番の挙動

17ポートの接続確認では、80・1935・3356・3357がopen。22/23/2323、554/8554等は接続拒否だった。全ポート走査ではないため、未調査ポートの不存在を意味しない。

80番は通常のGETで応答を得られず、HEADでは短いHTML、誤ったプロトコルの要求にはHTMLの400 Bad Requestを返した。標準HTTPのステータスヘッダーを確認できず、使える管理画面や制御APIは見つかっていない。HTMLの先頭を3357のバイナリ応答と解釈した初期推定は破棄した。未知の設定CGIの総当たりはしていない。

## 6. 実再生チェックで見つかった中継の停止

- 調査前：別Tailscaleノードで720p＋AACを約5秒、34フレーム復号。終了0、エラー0。
- 調査後の最初の確認：32秒でタイムアウト。TCP接続は通り、同ホストでもAAC情報は読めたがH.264のサイズが不明で映像を復号できなかった。
- このとき中継・publisherはsystemd上activeで自動再起動回数0だった。**プロセスの生存だけでは配信の正常性を判定できない**。
- 既存publisherと並行した新規カメラRTMP接続はhandshakeでタイムアウト。同時接続制限やカメラ側状態、取得処理の問題を切り分ける証拠としては不十分。
- 復旧：`iermu-rtmp.service` と `iermu-rtmp-publish.service` だけを設定変更なしで再起動した。カメラとネットワークは再設定していない。
- 復旧後：別Tailscaleノードで720p＋AACを約5秒、42フレーム復号。終了0、エラー0。

3356の調査が停止の原因か、既存RTMP側の別の問題かは未確定。長期安定性の改善完了とはしない。再発対策には、active監視ではなく「一定時間内に映像が実際に復号できるか」というヘルスチェックと、条件を分けた再現試験が必要。今回は監視・自動復旧の本番コードを変更していない。

## 次に検証するなら

1. 既存RTMPと3356の並行使用・切断が相互に影響するか、前後の復号確認を挟んで条件を1つずつ試す。
2. 3356のPTS/DTSを保持して映像・音声を多重化し、長時間の同期を測る。
3. 画質段階の値と解像度の関係は、設定バックアップと復元を用意した別試験で確認する。
4. スピーカーは接続種別・認証・publish受理を先に確定し、利用者が聞ける状態で最小限の実音確認を行う。
