# 使った手法と設計判断

この作業は「映像を中継するソフトを置くだけ」ではない。カメラの接続先、独自制御、古いクラウド通信、非標準メディア、家庭内経路をそれぞれ調べ、確認できた部分から組み合わせた。

## 1. レイヤーを分けた観測

- `iw`・hostapdの接続状態とjournal、モニター用無線インターフェース、tshark/dumpcap等で無線のprobe・関連付けを調べた。
- DHCP、ARP、ping、TCP/UDP、TLS、RTMPの順に確認した。pingが通ることを映像成功や設定保存成功の代用にはしない。
- 切断時刻とクラウド向けの再接続を照合した。原因仮説と、実際に観測したイベントは区別した。
- カメラへの変更は読み取り・バックアップを先にし、無関係なパラメータを一括で上書きしない方針とした。

## 2. AndroidアプリとARMネイティブコードの静的解析

入力は `com.intl.iermu`、versionName `1.8.0_1224`、versionCode 577のAPK。JADXでJava側、pyelftoolsとCapstoneでARM/Thumb共有ライブラリ側を読んだ。

- 設定コマンド、構造体、JNIからネイティブへの呼出しを手掛かりにした。
- `iermuffp_start_audio`、`iermuffp_stop_audio`、`audio_start`、`flv_wrap` とRTMPのpublish成功文字列の参照を調べた。
- `devtype`、`accesstoken`、`NetStream.Publish.Start` などの文字列を、コードから参照する箇所へ逆引きした。
- 静的解析で見つかった「送信経路」は、その機体でスピーカーが鳴った証明にはならない。

[入力ハッシュと確認したシンボル](../evidence/app-static-analysis.json)、[収録した解析補助ツール](../research/README.md)を参照。APK・SO・JDK・JADX本体はGitに含めない。

## 3. TCP 3357の独自制御を実装

要求は4バイトヘッダ `[main, sub, length_low, length_high]` と本体。通常応答は本体長がビッグエンディアンで、要求とは異なる。

| main/sub | 用途 |
| --- | --- |
| 5/17 | バージョン |
| 69/6 | ローカルログイン |
| 74/63 | 機体情報 |
| 74/38 | Wi-Fi構造体読出し |
| 72/8 | Wi-Fi設定 |
| 65/3 | 保存 |
| 74/41・75/41 | IR構造体の取得・設定 |

`75/63` の追加認証は機体種別を区別する必要があり、一律の必須手順とは扱わない。今回の初回セットアップ実装は `iMacType=0` を確認した経路である。

重要な修正は `ff00` の扱い。`41 03 ff 00` と `48 08 ff 00` は対象コマンドの成功ステータスで、65280バイトの本体長でも保存拒否でもない。一方、GET/SETパラメータへ同じ解釈を無差別に適用しない。

Wi-Fi本体97バイトではSSIDを1〜32、PSKを65〜96へ入れる。コマンド応答だけで終わらず、AP参加・DHCP・必要に応じて電源再投入後の保持まで確認する。詳細は[プロトコル](PROTOCOL.md)。

## 4. 無線APを利用して接続経路を制御

- カメラ用にはhostapdの専用SSIDとMAC ACL、dnsmasqの固定DHCPを用いた。
- 一時的に家庭用と同名の可視APを使って制御経路を回収した。BSSIDを狙うprobeがあるので、同名SSIDなら必ず自動移行するとは限らない。
- 常用は専用SSIDへ戻し、家庭用の同名APを残さない構成にした。
- 同じ無線機にAPとmanaged STAを作り、MACを分けた。STAは家庭用APと同じチャンネルに合わせ、省電力を切った。
- APの `.254` と家庭用ルーター `.1` を分離し、カメラの `/32` 経路とproxy ARP等で同一サブネットの重なりを扱った。汎用の無線ブリッジを作った、という構成ではない。
- 上流とデフォルト経路は有線のままにし、家庭用Wi-Fiから経路やDNSを勝手に置き換えない設定にした。

## 5. クラウド向け通信をローカルで受ける

- dnsmasqで対象ドメインをローカルへ向け、カメラに絞ったiptablesのルールでDNSや指定ポートを受信側へ誘導する。
- `fakecloud.py` はTCP 3399・UDP 3368等の受信と記録を担当する。パケットを受けたことと、APIを再現したことは別。
- カメラがSSLv3のClientHelloを送るため、通常の現代TLS設定だけでは相手をできない。tlslite-ngを使う別の8443番受信処理を追加した。
- 自己署名証明書、TLS設定、HTTP応答選択機構を用意した。既定応答は `200 {}`。メーカー全API・認証・トークン発行を再現したものではない。
- DNS・旧TLSは互換性のための局所的な受信処理で、通常の閲覧URLへSSLv3を公開する構成ではない。

## 6. 非標準RTMP/FLVを標準プレイヤー向けに補正

カメラ側のURLは `rtmp://192.168.10.34:1935/live/live`。PythonでRTMPハンドシェイク、AMF、チャンク、集約メッセージを処理し、FLVへ出力する。

今回の機体はH.264 Pフレーム末尾に79バイト、AAC末尾に89バイトの独自データを付ける。プレイヤーがそれを圧縮データとして読むと、映像の更新がキーフレーム中心になったり音声復号が壊れたりする。

- 映像：長さ付きNALを解析し、有効な境界を求める。長さだけでは独自末尾をNALと誤認する場合があったため、forbidden bitが0でNAL typeが1〜23であることも検査した。
- 音声：89バイトを引いた候補位置でAAC END要素の条件を確認してから処理する。全ての入力から固定長を無条件に削る実装ではない。
- FLVのタグ長とPreviousTagSizeを修正し、標準出力へ逐次流す。
- FFmpegで映像・音声を実際に復号して検査した。出力時刻の丸め警告には1msの時間基準とpassthrough設定を使い、データ破損警告と区別した。
- 中継時はH.264/AACをcodec copyする。再エンコードで画質を落として問題を隠す方法ではない。

[補正コード](../client/fix_flv.py)、[受信検証](../evidence/control-verification-20261111.json)を参照。

## 7. IRは必要な1バイトだけ変更

パラメータ41の24バイトを取得し、他の閾値を維持したままオフセット4を0/1/2へ変更する。SETの成功応答に加え、映像のモノクロ化と自動への復帰を確認した。

GETが現在の動作モードを返さないことを踏まえ、読戻し値だけで成否判定しない。モノクロ化をIR LEDの照射証明とも扱わない。

## 8. Tailscaleの内側で中継

```text
カメラRTMP → Python受信 → FLV補正 → FFmpeg（copy）
                                            ↓ publish
                                   MediaMTX / live/camera
                                            ↓ read
                                   Tailscale上のVLC等
```

- MediaMTXを公式チェックサム照合のうえ導入。Tailscale IPv4だけにbindする。
- publishを同ホストからに、readをTailscale IPv4範囲に限定し、TailscaleのACLも適用する。視聴専用のアプリ認証アカウントを発行したわけではない。
- RTMP自体は平文だが、Tailscale経路の通信はオーバーレイで暗号化される。インターネットの1935番へポート開放する必要はない。
- カメラを各視聴端末から直接読まず、常駐publisherが一度取得したものを中継する。カメラ側の接続競合を避ける狙いがある。多数同時視聴の負荷試験は未実施。
- systemdで常駐化し、失敗・ソース終了時の再起動と依存サービスとの連動を設定した。実ホスト再起動の検証とは区別する。

## 9. 成功の判定と保管

「送れた」「ポートが開いた」「メタデータを見た」だけでなく、映像・音声の復号、AP再参加、DHCP、pingを個別に記録する。初回、補正前、補正後、Tailscale別ノードの検証を混同しない。

Gitにはコード・例示設定・検証要約を置き、私用バックアップや部屋の映像を置かない。旧版は `reference/` で保存し、現行版と分離する。
