# SDKによるトークン取得・配信先決定の解析

## 結論と到達点

このファームウェアのネイティブ送信は、単一のRTMP URLを設定して終わる構造ではない。

1. メーカーAPIから `upload_token`、`connect_cid`、`config` を取得する。
2. `config.init` の文字列をSDKのINI設定として扱い、トークンの4要素と組み合わせる。
3. INIのTracker一覧を読み、独自UDPプロトコルで接続先IP・ポートを選ぶ。
4. 選ばれたIP・ポートとトークンからRTMP URLを構成し、SDKの接続処理へ渡す。

**実機のカメラ→Linux自動プッシュは、まだ成立していない。** 今回は静的解析と、実ファームウェアのARM命令を用いた23ケースのオフライン検証まで。現在の映像取得、DNS、応答ルール、Wi-Fi、サービスは変更していない。Telnetログインや認証情報は、この解析方法の前提ではない。

```text
メーカーAPI: getuploadtoken
  ├─ upload_token = CID_TokenControl_TokenExpire_TokenStr
  ├─ connect_cid（別フィールド）
  └─ config
       ├─ api_url（SDKのAPIホスト。最終RTMP配信先ではない）
       └─ init（SDK用INI文字列）
             └─ [Tracker] Count / IP1 / Port1 ...
                         ↓ 独自UDPでサーバ選択
                  配信先IPv4 + ポート
                         ↓
rtmp://<選択IP>:<選択ポート>/live/<CID>_<TokenControl>_<TokenExpire>_<TokenStr>
```

## 対象と解析方法

対象は [cmsMain.out](../firmware/iblack-8m/extracted/camera_modules/cmsapp/cmsMain.out)。以下はこのSHA-256のARM32 little-endian ELFだけに対応する仮想アドレスで、他版へそのまま適用できない。

```text
4419e7f86607eb83337de021563db2bb7392040059b29b715090e2ba54572e56
```

- ELFのインポート、書式文字列、PIC/GOT参照、分岐先、状態変数の読書きを照合した。文字列が存在するだけで「使用される設定」とは判定していない。
- UDP応答の分岐、実際の受信ラッパーとディスパッチ、CRC32、16進デコード、接続先取得関数をUnicornで部分実行した。
- ネットワークI/Oは合成入力へ置換し、未モデル化のPLT呼出し・ARM割込み／システムコールを停止する。実機や外部サーバには接続しない。
- SDKの文字列はTopvdn、バージョン `1.6.7.0`、ビルド `2017-03-28 16:40:28` を示す。

## 1. メーカーAPIとSDK初期化

`0xba5dc` の `cmsGetLyToken` は、次の形式のHTTPS要求を組み立てる。実際の機体識別子・署名・トークン値は記録に含めない。

```text
/v2/pcs/device?method=getuploadtoken&deviceid=%s&time=%u&client_id=%s&sign=%s&request_no=%s&utc=1
```

| 読取箇所 | 内容 | 確認できた範囲 |
| --- | --- | --- |
| `0xba7d8` | `upload_token` | SDKへ渡るトークン文字列 |
| `0xba7ec` | `connect_cid` | 別の接続IDフィールド。トークン内CIDと同一とは断定しない |
| `0xba8a0` / `0xbaef8` | `config` | 欠落時は失敗。HTTP 200と空JSONだけでは不足 |
| `0xbaa6c` ～ `0xbab08` | `config.init` | 文字列として取得し、長さに応じてコピー／割当て |
| `0xc8a58` 内の `0xc8adc` など | SDK開始 | トークン、SDK設定、コンテキスト、コールバックを渡す |
| `0xdba50` → `0xdc8c0` | 開始API本体 | トークンを解析し、SDKの初期化へ進む |

`config.init` はここではSDK用の**INI文字列**であり、「initというJSONオブジェクトを適当に返す」実装では一致しない。`config.api_url` の既定値に現れる `api.topvdn.com` はAPI側のホストで、映像の最終送信先を直接指定する欄ではない。

`config` にはビットレート、音声、録画、共有、タイムゾーンなどの処理もある。実機用応答では現在値と適用条件を保持する必要があり、`config: {}` の投入は行っていない。

## 2. トークンの形式とINIへの組込み

`0xdc8c0` と `0xe5044` は、次の書式で4要素を読む。

```text
%u_%u_%u_%s
```

対応するSDK設定項目は `CID`、`TokenControl`、`TokenExpire`、`TokenStr`。4要素を読めない場合は開始処理が失敗する。項目名から有効期限などの用途は示唆されるが、署名の妥当性、有効期限の検証、クラウド側の受理条件まで再現したわけではない。

初期化処理の書式文字列は次のとおり。末尾の2つの `%s` には、解析したTokenStrと、渡されたSDK設定の先頭から**8バイト先**の文字列が渡る。

```text
[Config]\r\nCID=%u\r\nTokenControl=%u\r\nTokenExpire=%u\r\nTokenStr=%s%s
```

8バイトは `[Config]` の文字数と整合するが、呼出元設定の先頭検証や全ての組合せは未確認。実機で使える完全なINIのひな形とは扱わない。

INIを読む `0x102194` はTokenStrを `0xf5098` へ渡す。この関数は2文字ずつ `strtol(..., 16)` でバイト化する**16進デコーダ**だった。32桁の合成16進文字列は16バイトになり、奇数桁の末尾1文字は今回の条件では処理されない。これを暗号解読の成功とは呼ばない。

なお、途中の `0xdcfc8` は `[LogServer]` を読むログ初期化であり、クラウドから設定を取得する関数ではない。

## 3. TrackerはDNS名ではなく数値IPv4

INIパーサ `0x102194` の `0x102550` 以降は、`[Tracker]` の `Count`、`IP%u`、`Port%u` を読む。

- `IP%u` は `0x1025b4` で `inet_addr` へ渡る。ここは数値IPv4の解析で、ホスト名のDNS解決ではない。
- `Port%u` の既定値は80。この値はパーサの既定値であり、全環境で実際に80番を使うという意味ではない。
- TrackerはIP4バイト＋ポート2バイトの6バイト単位で保持される。

**したがって、クラウドのDNSだけLinuxへ向けても、INIに埋め込まれたTracker IPやUDP応答が返す数値IPは書き換わらない。** DNS誘導はメーカーAPI要求をLinuxで受ける手段にはなるが、映像の経路決定を最後まで代替するものではない。

## 4. 配信先を返す76バイトUDP応答

受信経路は `0xf911c` → `0xfdca8` → libc `recvfrom` → `0xff248`。今回検証した分岐は次の条件を持つ。

| オフセット／条件 | 内容 |
| --- | --- |
| 全長 | 76バイト（`0x4c`） |
| `+4`、4バイトLE | コマンド値 `0x01010818` |
| `+8`、1バイト | 成功時0 |
| `+0xc`、6バイト | 選択先IPv4のuint32 LE ＋ ポートのuint16 LE |
| 送信元 | 選択済みTrackerのIP・ポートと一致すること |
| SDK状態 | 2であること |
| モード | 今回の対象は2～6。モード1は別分岐 |
| 受信オブジェクト | `+0xc` の値が0であること |

成功すると状態が4へ進み、6バイトの接続先がグローバル領域 `0x4891f4` にコピーされる。`0xf720c` は開始時の状態1から選択待ちの2へ進み、完了を待って接続先を呼出元へ返す。**既に状態4のまま入れた場合は、今回の関数では出力バッファをコピーしない**ため、単純な状態の強制設定は正しい再現にならない。

CRC32関数 `0xee238` は標準の反転CRC32と一致した。別の送信ビルダ `0x100110` は120バイト、コマンド `0x01010901` のパケットを作り、先頭4バイトにCRC32を置く。ただし、これが76バイト応答に対する要求コマンドだとはまだ結び付けていない。

**今回の76バイト受信経路では、CRCを意図的に壊した合成応答も受理された。** パーサ単体だけでなく、受信ラッパー・ディスパッチを通すオフライン実行でも確認した。ただし、初期登録、全コマンド、実クラウド、他ファームウェアに検証なしで一般化しない。公開する合成応答は、実機用サーバの完成済み応答テンプレートではない。

## 5. 最終RTMP URLと未解析の接続処理

接続先が得られると、SDKは次の2段階でURLを作る。

| 箇所 | 書式 |
| --- | --- |
| `0xdbd88` ～ `0xdbde4`、文字列 `0x3142eb` | `rtmp://%s:%d/live/` |
| `0xdbf08` ～ `0xdbf2c`、文字列 `0x3142fe` | `%s%u_%u_%u_%s` |

したがって最終形は以下になる。

```text
rtmp://<発見されたIP>:<発見されたポート>/live/<CID>_<TokenControl>_<TokenExpire>_<TokenStr>
```

現在のLinux配信パス `live/camera` / `live/camera2` とはストリーム名が異なる。既存の受信サーバにそのまま流せるとは限らず、別待受と対象を限定したpublish許可が必要になる。

`0xdbf54` は `0xe35e0` の `GetEncryptInfo` も呼ぶ。SDK固有の情報付加、RTMPハンドシェイク、publish、音声、再接続との関係は未解析であり、**標準RTMP互換とも非互換ともまだ断定しない。** 文字列から接続先の構成は確認したが、実機でのRTMP publish完了とは別の到達点である。

## 6. オフライン検証の範囲

[ARM部分実行ツール](../tools/sdk_upload_probe.py) と [単体テスト](../tests/test_sdk_upload_probe.py) を追加した。

| グループ | ケース数 | 検証内容 |
| --- | ---: | --- |
| UDPパーサ | 12 | モード2～6の成功、送信元IP／ポート・状態・長さ・コマンド・status・transportの不一致 |
| 受信ループ | 4 | 正常、CRC不一致、送信元不一致、短い応答。実受信ラッパーとパーサへ到達 |
| CRC32 | 3 | 空、既知ベクトル、合成応答の本文をPythonのCRC32と照合 |
| 16進デコード | 3 | 小文字、大文字、奇数長の合成TokenStr |
| 接続先取得 | 1 | 状態1→2、受信完了をモデル化した後の6バイト返却 |
| **合計** | **23** | **全ケース成功** |

実行前に状態や選択済みTrackerをテスト条件として設定している。接続先取得ケースでは別受信スレッドの完了をsleep境界でモデル化し、SDK全体の並行実行はしていない。libcのメモリ操作・文字列操作、ログ、時計も必要な範囲だけモデル化している。全ブートシーケンス、トークン発行、登録、heartbeat、実RTMP通信の成功を示すテストではない。

### 再現方法

リポジトリのルートで実行する。使用した任意依存はUnicorn 2.1.4、pyelftools 0.32。命令の静的確認にはCapstone 5.0.3も用いたが、この再現ツール自体にCapstoneは不要。実機のIP、認証情報、ネットワーク接続は不要。

```bash
python3 -m pip install 'unicorn==2.1.4' 'pyelftools==0.32'
python3 -B tools/sdk_upload_probe.py --output /tmp/sdk-upload-offline-report.json
python3 -B -m unittest discover -s tests -p 'test_sdk_upload_probe.py' -v
python3 -B tools/verify_repo.py
```

任意依存なしでも合成入力のテストは動き、ARM実行が必要な2つの単体テストはスキップされる。対象ファームウェアのハッシュが異なればARM実行を拒否する。`-O` でアサーションを無効化する実行は許可しない。

## 次の実装で必要なもの

1. 現在値を保持し、機体IDを非公開設定で照合した `getuploadtoken` 応答を用意する。NAT後の送信元IPだけで機体を区別しない。
2. SDKの登録・Tracker選択・heartbeatと要求／応答対応を復元する。今回の76バイト分岐だけでは、電源投入からの接続開始を代替できない。
3. Tracker設定と応答でLinux有線IP `192.168.1.201` および専用受信ポートへ誘導する。カメラはAtermのWi-Fiを使い続けるが、Linux側の受信インターフェースを有線にする目標。
4. 本番と別の待受・パスでRTMPハンドシェイク、publish、トークン名の扱い、映像・音声・再接続を検証する。既存配信を上書きせず、元の応答へ自動復帰できるようにする。
5. `ens18` に実際に映像パケットが届き、復号・連続運転できてから切替を判断する。LinuxのWi-Fi停止は、2台と関連サービスの依存を全て外した後。

今回の成果は「Linuxでクラウドを代替するために必要な層が具体化した」こと。**まだ完成したクラウド代替サーバや、有線だけで動く映像配信を提供したものではない。**
