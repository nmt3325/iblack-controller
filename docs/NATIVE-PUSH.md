# カメラからLinux有線IPへの自動送信：調査と未完了点

## 状態

**未切替。ネイティブRTMP自動プッシュは成立していない。** LinuxのWi-Fiは維持している。Telnetを起動できることと、OSへログインできることは別であり、rootシェルはまだ取得していない。

今回の目標はカメラのEthernet化ではなく、次の経路でLinuxのWi-Fiを不要にすること。

```text
カメラ -- Wi-Fi --> Aterm -- 有線側ネットワーク --> Linux 192.168.1.201
                                                   |
                                                   +--> Tailscale経由で視聴
```

現行の視聴はLinuxがカメラへ接続して映像を取得するpull方式。カメラ2への経路は `dev wlp1s0 src 192.168.10.22` であり、有線だけへの移行は完了していない。

## 今回の非破壊確認

- Linux上からTailscale IP宛の `live/camera` と `live/camera2` を開き、それぞれ動画3フレームを復号できた。FFmpegの終了コードは両方0。外部ノードからの再試験や長期連続運転を意味しない。
- 追加のフレーム数確認では、1台目は3フレーム成功、2台目は一度終了コード183・0フレームだった。2台目を単独で接続し直すと3フレーム成功した。サービスの手動再起動は行っておらず、連続安定性は未確認。サービス状態を問い合わせたコマンドにも一度タイムアウトがあった。
- カメラ2のTCP23はTelnetのネゴシエーション後に `login:` を返した。OSのユーザー名・パスワードは送っていない。1台目のTelnet有効化は未試行。
- HTTPS代替サーバの既存ログに `GET /v2/pcs/device?method=getuploadtoken` を確認。有線IPで受けたクラウド制御通信の証拠であり、映像の有線受信成功ではない。NAT後の送信元のため、各要求をどちらの機体かには同定していない。
- API応答ルールは空で、既定応答は `200 {}`。今回この応答、DNS、カメラ設定、systemdサービス、Wi-Fiは変更していない。
- DNS設定の再読取りはリポジトリ内クライアントに既存CMS認証情報を読み込ませられず未完了。このローカル設定エラーをカメラのDNS故障とは判定していない。

時刻・復号結果・ログ抜粋の件数は [匿名化した検証記録](../evidence/native-upload-wired-investigation-20261113.json) に保存。

## なぜRTMPのURLを差し替えるだけでは済まないか

対象は [cmsMain.out](../firmware/iblack-8m/extracted/camera_modules/cmsapp/cmsMain.out)、SHA-256:

```text
4419e7f86607eb83337de021563db2bb7392040059b29b715090e2ba54572e56
```

| アドレス | 確認した処理 | 意味・限定 |
| --- | --- | --- |
| `0xba5dc` | ログ名 `cmsGetLyToken`、`getuploadtoken` をHTTPS要求 | 送信前のメーカーAPI依存がある |
| `0xba7d8` / `0xba7ec` | `upload_token` / `connect_cid` を応答から取得 | トークン文字列と接続IDがSDKへ渡る |
| `0xba8a0` / `0xbaef8` | `config` を取得、欠落時は失敗 | 空JSONの成功コードだけでは送信開始を再現できない |
| `0x30f444` | `rtmp://%s/live/%s` の書式 | 文字列の存在だけでは設定機能の証拠にならない |
| `0xbe3f8` → `0xc7390` | URLを引数に呼ぶが、コンストラクタはその引数の `r0` を使用前に上書き | このビルドのこの送信経路では、整形されたURLがそのまま接続先になるわけではない |
| `0xc83f8` | ログ名 `cmsLY_StartRtmpConnect` | 専用SDKの接続処理へ進む |
| `0xdb990` → `0xdbe50` → `0xe3ff0` | SDK内部の接続手順 | デバイス状態・サーバアドレスの取得も必要 |
| `0x315277` / `0x315295` | RTMPサーバIPが `0.0.0.0` の場合のエラー文字列 | SDK側で実際の配信先IPを決めていることを裏付ける |

`config.api_url` の既定ホストには `api.topvdn.com` が入るが、これは最終的なRTMP公開先URLと同一とは確認していない。`ttt` という初期サーバ文字列もあり、URL書式だけを見たパッチは不十分。

ここから「標準RTMPに送れない」とまで断定はしていない。専用SDKのサーバ取得応答と、Linux側受信サーバとの互換性は未検証。

## APIの成功応答を無造作に返さない理由

`getuploadtoken` の `config` パーサには、ビットレート、音声、共有、録画、タイムゾーンなどの処理も含まれる。省略時の既定値と適用条件を検証せずに `config: {}` を返すと、送信先以外の設定に影響する可能性がある。

また現在のHTTPSサーバのルールはURL部分文字列一致である。NAT後の送信元IPだけでは1台目と2台目を分けられない。機体IDを非公開設定で照合したルールと自動ロールバックを用意するまで、全機体共通の成功応答は適用しない。

## 次の実装条件

1. **Telnet経由の場合:** OS用の正しい認証情報でログインできることを確認し、稼働中プロセス、設定ファイル、利用可能な送信プログラムを読み取り専用で確認する。3357のCMS認証情報とOS認証情報は同じとは仮定しない。
2. **Telnet不要の代替:** メーカーAPIとSDKのサーバ取得応答を再現する。設定変更の適用条件をオフラインで検証し、現在値を保持したカメラ2限定の応答を使う。これはまだ実装していない。
3. Linux側には本番と別の公開パス／待受を用意し、必要な送信元・パスだけに公開を許可する。既存の `live/camera2` をいきなり上書きしない。
4. Linuxの `ens18` への実パケット到着、送信元、映像復号、音声、再接続を確認する。Linux自身から有線IPを開けることだけで成功にしない。
5. カメラ2の代替経路が安定してから切替を行う。1台目、DNS、制御・監視サービスにもWi-Fi依存が残っていないことを確認した後に限り、LinuxのWi-Fiを停止する。

ファームウェア書換え、未解析更新コマンド、パスワード推測のオンライン試行、ルーター設定変更は今回行っていない。
