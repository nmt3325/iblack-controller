# カメラ自身のDNS設定

## 到達点と未確認事項

DNSの表示・変更プレビュー・明示適用・保存・DNSだけの復元を `client/camctl.py` に追加した。ルーターやLinuxホストのDNSを書き換える機能ではない。

**対象実機でDNS書込み・保存後再接続・実効DNSを確認した。** 後でカメラが通常Atermの `.10.35` にいることが分かったため、前回の専用APアドレス `.10.34` への到達不能をカメラの電源断とは扱わない。現在は固定IP `.10.35`、主DNS `.1.201`、副DNS `.10.22`。DHCP有効の最初の書込みは読出しが旧値で保存せず、次にDHCP無効化とAPKの設定→保存順序を用いて一致・実通信を確認した。[現行構成・検証範囲](HOME-AP.md)を参照。

追加した `--app-save-sequence` は、明示的に選んだ場合だけ保存を読出しの前に送る。適用には `--apply --save --experimental` が必要。`--static` はこの順序と一緒にのみ使え、現在IP等を保持してDHCPを無効化する。既定の読出し先行の保護は従来どおり。不明なファームウェアへ一般化しない。

## 使い方

稼働機では、既存の私用認証設定をそのまま使う。

```bash
cd /home/nmt3325/iermu_cam

# 読取りのみ。DNS・IP・ゲートウェイ・DHCPフラグを表示
python3 camctl.py dns

# DNS_IPを変更先IPv4アドレスとして指定した後、変更内容をプレビュー
python3 camctl.py dns-set "${DNS_IP:?変更先DNSのIPv4アドレスを指定}"

# セカンダリ省略時は現在値を保持。不要なフォールバックを残さない場合のプレビュー
python3 camctl.py dns-set "${DNS_IP:?}" --secondary 0.0.0.0

# 実機検証用の適用。まだ永続保存はしない
python3 camctl.py dns-set "${DNS_IP:?}" --secondary 0.0.0.0 --apply --experimental

# 再度プレビューして確認後、適用と保存を一度に行う場合
python3 camctl.py dns-set "${DNS_IP:?}" --secondary 0.0.0.0 --apply --experimental --save
```

**同じ値のまま再実行した場合は何も送らないため、後から `--save` を足しても保存だけは行わない。** 永続保存も試す場合は、変更を適用する最初の操作で `--save` を指定する。事前に非永続の実機試験をする場合は、試験前DNSへ戻したことを確認してから、目的のDNSを `--save` 付きで設定する。通信断時に操作を連打しない。

リポジトリ側からは `python3 client/camctl.py ...`。認証は `CAMERA_USER` と `CAMERA_PASSWORD` を環境変数で指定する。認証値を引数やGitへ入れない。接続先変更は `--host` または `CAMERA_IP`。

## 既定の書込み安全手順（読出し先行）

1. 入力がIPv4か検査する。ホスト名、IPv6、マルチキャスト、ブロードキャスト、プライマリの `0.0.0.0` は拒否する。
2. **その場で実機から読んだ**44バイトを使用する。古いアーカイブ全体を実機へ流し込まない。
3. DNS欄16〜23以外を完全に保持する。IP・ネットマスク・ゲートウェイ・DHCPフラグ・MAC等は変更しない。
4. 適用前に元の本文を私用 `stab/backup-param-8-*.bin` へ排他的に作成し、ファイル権限を0600にする。Gitには入れない。
5. `75/8` を送り、想定した成功応答だけを受け入れる。
6. `74/8` を再読取りし、DNS以外も含めて要求本文と完全一致するか検査する。
7. **`--save` 指定時だけ**、一致確認後に `65/3` を送り、さらに再読取りする。エラーを無視した保存や、未確認の追加認証・再起動はしない。

異常時は非ゼロ終了し、失敗段階・バックアップ場所・確認できた状態をJSONで返す。設定送信後に通信が切れた場合、結果は不明であり、自動的に失敗前の値へ戻ったとは判断しない。

## DNSだけを戻す

```bash
python3 camctl.py dns-restore /path/to/backup-param-8-TIMESTAMP.bin
python3 camctl.py dns-restore /path/to/backup-param-8-TIMESTAMP.bin --apply --experimental --save
```

復元ではバックアップから**DNS2欄だけ**を取り出し、現在の実機設定へ適用する。古いIP・ゲートウェイ・MAC等を丸ごと戻す操作ではない。44バイト本文のバックアップのみを受け付ける。

## 実効DNSとDHCPに関する注意

- DHCPフラグは自動で無効化しない。DHCPによってDNSが上書きされる可能性がある。
- `readback_verified` は設定本文の読戻しだけ。`saved` は保存応答と直後の読戻しだけで、実際の名前解決先や再起動後の保持は意味しない。
- `effective_dns_verified` と `reboot_persistence_verified` は、このCLIでは常にfalse。実機のDNS問い合わせ先の観測と、必要に応じた物理電源再投入試験が別途必要。
- ローカルへクラウド名を向けたい場合、セカンダリに外部DNSを残すと意図しないフォールバックになり得る。
- 現行Linux側のDNS転送ルールはそのままなので、設定欄だけでなく転送前の問い合わせ宛先も確認する。
- DNS変更だけでは、カメラが固定IP宛てに送る通信は誘導できない。

## オフライン検証

追加の22テストを含め、全43テストが成功。DNS以外の全バイト保持、プレビュー無書込み、明示フラグ、バックアップ権限、応答不正・通信断・読戻し不一致時の保存抑止、DNSだけの復元を検査した。全て模擬通信であり、実機書込み成功の証拠ではない。

```bash
python3 tools/verify_repo.py
```

## APKと同じ保存先行の明示経路

通常Atermへの移行で確認した手順は `--app-save-sequence`。詳細・コマンドは [HOME-AP](HOME-AP.md) を参照。成功応答を確認して65/3を送り、一時切断後は新しい接続で全44バイトを照合する。再接続は有限回で打ち切り、設定送信は反復しない。失敗時は保存応答を受けたかと完全一致を分けて報告する。`dns-restore` もこのフラグを受け付けるが、バックアップから戻すのはDNS欄だけで、以前のDHCP・IPは復元しない。

拡張分の11件を加え全54件をオフラインで確認し、配備後は現在値の読取り・同一値プレビューを実行した。CLI拡張後に同じ値を不要に再書込みしてはいない。物理電源再投入による保持は未確認。
