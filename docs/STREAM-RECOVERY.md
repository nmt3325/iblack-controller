# ストリーム停止の修復 — 2026-11-12

## 修復後の構成

- 視聴URLは `rtmp://100.87.20.49:1935/live/camera` のまま。
- カメラは通常の家庭用AP、IPは `192.168.10.35`。本修復ではカメラの設定、DNS値、ファームウェア、電源を変更していない。
- Linuxは仮想STAをやめ、物理無線 `wlp1s0` 一つで接続。既存の `192.168.10.22/24` を固定設定で維持し、重複アドレス検出を3秒に設定した。Wi-Fi認証は通ったがDHCPのIP取得が失敗したため。
- 有線 `192.168.1.201` とTailscale `100.87.20.49` は変更していない。カメラへの経路は `192.168.10.35 dev wlp1s0 src 192.168.10.22`。通常のデフォルト経路は有線のまま。
- NetworkManagerの `iermu-home-uplink` に自動接続、優先度100、再試行回数0（無制限）を設定。旧仮想STAと旧汎用プロファイルは自動接続を無効化した。
- `wlp1s0` の古い厳格なunmanaged指定を解除。走査MACランダム化は当該インターフェースだけ無効化。接続時の非公開固定MACはNetworkManagerが管理する。
- 起動時準備スクリプトは物理STAモードで手動のMAC・リンク変更をしない。NetworkManagerとの競合を避ける。
- 家庭用受信のiptablesルールは無線側インターフェースを `wlp1s0` に更新。DNSの有線・無線側待受けは両方とも `api.iermu.com` を有線IPへ応答することを確認した。
- 中継起動前にはcarrier、送信元IP、カメラへの直接経路を読み取り専用で確認。無関係なデフォルト経路へ接続試行を繰り返さない。

## 停止の原因と試行の区別

最初の障害時は仮想STAが切断されIPv4を失い、カメラへの経路が有線側の別ネットワークのゲートウェイへ落ちていた。中継サービスは約1,170回の再起動を繰り返していた。未使用の物理無線がUPのままだったことで、仮想STAのMAC変更が `Device or resource busy` になっていた。

最初に物理インターフェースをDOWNにすると映像・音声は復旧したが、その後の切断試験では仮想STAの自動復旧を安定して実証できなかった。明示的な接続要求と標準自動接続の競合も観測した。実験用タイマーと書込み型の復旧処理は最終構成から取り除き、単一の物理STAをNetworkManagerだけに管理させた。未成功の試行を成功扱いにはしていない。

15:38:26には最終方式でも `BEACON-LOSS` を観測し、15:38:37にNetworkManager／wpa_supplicantだけで再接続した。この間RTMPクライアントの接続は切れ、サーバー側の中継は標準の再起動ポリシーで再開した。したがって「無線切断がなくなった」「クライアントに無瞬断で配信できる」とは主張しない。

## 最終確認

- 別のTailscaleノードから、映像と音声を同時に復号。
- 記録時刻: `2026-11-12T15:41:39.876117+09:00`。
- 要求60秒、復号メディア時間 **59.961秒**、映像 **508フレーム**、復号エラー0件。
- 映像: H.264 Baseline、1280×720。マイク: AAC-LC、11025Hz、モノラル。
- 映像・音声ファイルは保存せずnull出力で検証。
- 起動・受信・DNS・中継の5サービスはactiveかつ自動起動を有効化。ホスト再起動そのものは実施していない。
- 読み取り専用の経路ガード17件を追加し、既存64件と合わせオフライン81件。
- 根拠: [修復・最終再生記録](../evidence/stream-repair-20261112.json)。

## 運用上の限界

- 数日単位の安定性とホスト再起動後の実動作は未検証。無線のbeacon loss自体を根治したとは言えない。
- 無線が切れた場合サーバーは再接続を試みるが、VLC等の視聴側は再度URLを開く必要がある場合がある。
- カメラ `.35` とLinux `.22` は固定IP。家庭用ルーター側でDHCP予約または配布範囲からの除外を行うことを推奨する。ルーターの設定は変更していない。
- 現行配信はLinuxがカメラをpullして中継する方式。カメラ自身のクラウド自動pushを成立させたものではない。
- 専用APへの復帰には別途構成の切替が必要。旧AP専用設定を現在の物理STAモードへそのまま適用しない。
